RT-safe: 3 ms process() budget, drops lowest-priority voices if exceeded.

  - **Consume `MusicalContext`** (key, rootPc, scale, energy, style, section, beatsPerBar) for sample selection / pitch quantization.
  - **Consume `NoteEvent`** `{type:'note', note:MidiNote, velocity:0..1, duration:sec, channel:string, at:AudioTime}` — trigger the appropriate sample voice at the scheduled audio time.
  - **Use `VoicePool<V>` from `@psy-foundation/dsp`** — preallocate sampler voices, round-robin allocation, voice stealing when full, no GC in hot path. Voice must implement `Voice` interface (active/noteOn/noteOff/panic). Pattern shown by `KickVoice` in `packages/music/src/audio/kick-voice.ts`.
  - **Use `AudioContext.currentTime` as the only clock** — pass as `nowFn` to Transport, schedule voices via AudioParam ramp methods, never use Date.now().
  - **Manage sample buffers** — likely via a new `Material` payload kind (e.g. 'sample' or 'audio-buffer') OR via `PresetPayload {engine:'sampler', params:{sampleId, rootNote, ...}}` referencing an external sample store. Foundation has NO sample-buffer type currently; the sampler device would own its sample store.
  - **Be deterministic & headless** — no UI in the device itself; UI is a separate concern (foundation rule: "Transport ≠ renderer ≠ radio ≠ UI"). Same transport/context/event sequence = same audio output.
  - **No musical policy** — foundation rule: "No device policy." The sampler plays what NoteEvents tell it to play; it does NOT decide what to play. Orchestration/composition is upstream (CompositionEngine, scheduler, learning).
  - **Be transport-agnostic** — work over any `Channel` impl (in-memory now; BroadcastChannel/WebSocket/WebRTC/Web MIDI/Ableton Link future).
  - **Runtime scheduler adapter needed** — foundation's scheduler is offline-only (plan→events[]). A sampler device needs runtime scheduling with lookahead (~150ms) + 16th-note-from-beat-grid + stale-event dropping. This is GAP-S1/S2/S3, currently unimplemented in foundation; PSY4's runtime scheduler is the reference.
  - **Fit the genre/style system** — MusicalContext.style field supports values like 'full-on', 'psytrance', 'techno', 'trance', 'progressive', 'dark-psy', 'goa' (per PSY5/PSY6 conventions). Sampler should respect style for sample selection.
  - **Report latency** — implement `reportLatencyMs()` so the host can compensate scheduling.
  - **Test via consumer contract pattern** — follow `integration/psy4-consumer-fixture/consumer-fixture.test.ts` pattern: prove the sampler is a "dumb consumer" that makes zero musical decisions, JSON-serializable state, deterministic, <100ms latency, no AudioContext/DOM/window references in pure-logic paths.
